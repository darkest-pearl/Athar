# Architecture decisions
Confirmed Android stack: Kotlin + Compose; Room for local completion and versioned attempts; Media3 ExoPlayer for bundled/local document audio. Single app, no server or account infrastructure. iPhone follows Android launch.

Development ID dev.elm.prototype is a placeholder; label Athar · prototype is a development label. Target/compile SDK 35, min SDK 26. Pinned conservative build: AGP 8.6.1, Gradle 8.10.2, JDK 17, Kotlin 1.9.24 + Compose compiler 1.5.14, Compose UI 1.6.8, Material3 1.2.1, Activity 1.9.2, Room 2.6.1, Media3 1.4.1, coroutines 1.8.1. Existing cached AGP/Kotlin/wrapper motivated this stable baseline. Upgrade/recheck Play target requirements before release; this demo is not a publication build. Official compatibility: https://developer.android.com/build/releases/agp-8-6-0-release-notes and https://developer.android.com/jetpack/androidx/releases/compose-kotlin. Room/Media3 release references: https://developer.android.com/jetpack/androidx/releases/room and https://developer.android.com/jetpack/androidx/releases/media3.

Room drives completion, review, bookmarks, and study-day UI via Flow. First completion per lesson/version is unique and saved answer events are immutable; replay cannot overwrite earlier incorrect evidence. Distinct completed sessions can earn study credit without inflating completion counts. No points or piety score are computed. Completion awaits storage before success UI. UI survives ordinary configuration changes via rememberSaveable; committed actions survive process death. Unsubmitted quiz state is not guaranteed after force-stop.

Study timezone is pinned to device zone at first use and persisted. UTC timestamps plus local study day and zone are stored for completed sessions; injected Clock/ZoneId allow midnight tests. Concept review uses the 1/3/7/14/30-day development schedule detailed below, with separate immutable events for later recall, hints, and reveals.

Audio sources: 12s neutral tone in assets, read-only document URI permission, or debug-only private representative.mp3 used by verification. Technical clipping range 0–30s explicitly unreviewed. Full original available. Position preferences saved on pause/background; no background service yet. Quiz navigation does not pause audio; backgrounding does. No INTERNET permission, telemetry or secret credentials.

Guest storage has no backup/sync; allowBackup=false. App removal/data clear removes progress. Future repositories can synchronize approved packs and per-user events without making UI depend on a network. Download/sync remain later work; bookmarks, review state, and study days are local. Content/publication metadata remains independent of presentation.

Production work still requires reviewed content, a real Tigrinya localization, audio focus/interruption checks, scoped publishing/auth rules if added, migration/backup design and prelaunch Sheikh review.

## Milestone 2 audio selection and timeline

The active source is explicitly Tone, Document, or Representative. Selecting a document through Android OpenDocument takes a persisted read grant and selects that exact URI. The private representative file is a deliberate development option; its presence cannot override a selected document. If the active URI is missing or access is revoked, the player clears media and asks for reselection without falling back. No broad storage permission is requested.

Resume keys include source kind, URI identity, and mode (full or technical range). Switching saves the old key before loading the next, and positions survive normal process restart. The prototype's old single-offset preference is read only when its exact media key matches. Media3 clipping presents a segment-relative player timeline: for a segment with source start `S`, full-recording source time is `S + playerPosition`; in full mode source time equals `playerPosition`. The current development technical range starts at 0 ms and ends at 30,000 ms or the file's earlier end. Its boundaries are unreviewed and are not teaching segments.

Playback remains foreground-only; backgrounding saves position and pauses. This test covered emulator decoding and positions, not audible quality, headphones, or interruptions on physical hardware.

## Content-driven milestone 2

The running app loads the portable bundled `fixture-pack.json` through `ContentPackParser`; the authoring copy in `content/` is byte-for-byte checked by tests. Lesson titles, notes, questions, choices, correct answers, and explanations no longer live in composables. UI chrome is in `res/values/strings.xml`. This pack contains two clearly marked neutral interface lessons and no religious instruction.

`ContentRepository` reads at most 256 KiB, validates schema, stable scoped IDs, types, collection bounds, authorization references, segment timestamps, and question source references before atomic activation. Android OpenDocument supplies an offline local pack; the app copies valid bytes into its private atomic file, so no broad storage permission or continuing document grant is needed. A failed import leaves the previously active pack and all learning rows untouched. Import rejects a changed pack at the same course/content version and changes to a currently active lesson under the same lesson version. Lesson versions must advance for corrected lesson material. Previously completed lesson versions remain in history; only a matching current lesson version counts as current completion. The first installed prototype's completion for `controls-fixture` version 1 remains current because that lesson is unchanged.

Room schema version 2 is exported in `app/schemas`. Explicit migration 1→2 retains the original Completion and Attempt tables and copies them into LessonCompletion and AnswerEvent. The legacy `q0` and `q1` events are assigned to `controls-fixture` with their original correctness, selected choice, version, and timestamp. New answer events are immutable and keyed by session, lesson, lesson version, question, and question version; duplicate delivery of one submission is ignored, while a later session creates new evidence. First lesson attempt is derived by query rather than overwritten. Bookmarks use stable lesson IDs. The app never uses destructive fallback.

Audio selection and positions are scoped by recording ID and segment/full mode. A bundled relativePath is resolved only within assets; an external file is explicitly associated with the pack recording ID through the document picker. The private representative file remains a labeled development override. Imported teaching content is metadata supplied locally, not independently authenticated editorial approval.

## Concept review scheduling

Room schema version 3 adds `ReviewState` through an explicit 2→3 migration; the 1→2 path remains registered. Matching-version completed lessons seed one review row per learned concept without replacing any existing row. Older completion and answer-event rows remain intact. A content-version change leaves old rows as history; only concepts and question versions present in the active pack are offered.

All due times are UTC instants. Completion seeds stage 0 due 24 hours after the completion timestamp. An independent correct answer to a due question advances stage 0→1 due in 3 days, then 1→2 in 7, 2→3 in 14, and 3→4 in 30; further independent successes remain stage 4 at 30 days. Wrong, hinted, or revealed answers reset to stage 0 due in 1 day. Immediate attempts before due and linked prerequisite recall record an answer event but do not advance the long-term schedule. The event and schedule update share one Room transaction; a repeated session/concept submission ID does nothing. This is a development default, not an optimized learning algorithm or a measure of mastery.

The Review area and Today count show current-version due concepts. A batch contains at most five distinct concepts; related already learned concepts are offered first and deduplicated against due items. This bounds catch-up after an absence. The fixture's second lesson links to a first-lesson concept as an optional recall check before its lesson quiz. Review explanations come from the active pack; the player can be opened after feedback for source replay. All study remains offline.

## Study days and streaks

Room version 4 adds immutable `StudySession` evidence and a unique `StudyDayCredit` row keyed by local study date. Migration 3→4 creates both tables and credits saved v3 lesson completions; the full 1→2→3→4 chain preserves original prototype rows. The saved `study-zone` setting is pinned on first use. Each event stores its UTC completion timestamp, derived date, and zone. A different device timezone later does not silently reinterpret saved dates.

Completing feedback for every question in a lesson session can earn a session, including low-scoring and repeat lesson sessions. The first completion record remains unique by lesson/version. Finishing a nonempty due-review batch after saving every due answer can also earn a session; optional before-due linked recall alone cannot. Session insert and day-credit insert share a Room transaction. Replaying the same session ID cannot add another session or credit; several legitimate sessions on the same date still produce one day.

The current streak is the consecutive run ending today, or ending yesterday until today finishes. After a missed day it displays zero while longest streak, total study days, lessons, and reviews remain saved. There are no hidden grace days or freezes. These values describe participation, not piety or mastery. Feedback is a static saved-state panel with no required animation, so reduced-motion settings have nothing to suppress in this milestone.

## Milestone 3 versioned learning state

Room version 5 adds an explicit `courseId` to lesson completions, answer events, bookmarks, and review state. Review state and bookmarks use `(courseId, conceptId)` and `(courseId, lessonId)` keys respectively. New completion and study-session IDs include the course. Study-day credit deliberately remains learner-wide: two courses on one local date earn one day. Original prototype `Completion` and `Attempt` tables remain readable legacy evidence; all new learning writes use the course-scoped tables. Migration 4→5 attributes only the known `controls-fixture` and `study-tools-fixture` lessons to `controls-course`. Other v4 lesson and answer rows survive as `legacy-unattributed`; no course progress is inferred from them. No destructive migration fallback is enabled.

On pack load, review reconciliation considers completions for the active course and current lesson versions. It chooses one source per concept, preferring an existing source when its lesson, question, and question version still match, then the most recent qualifying completion with stable ID tie-breaks. A lesson-version update with the same question identity and version retains the schedule and updates the source lesson version. A changed question version or source resets the active concept to stage 0, due one day after the qualifying completion; this deliberately avoids carrying a mastery claim onto corrected material. A removed concept has no active queue row until a valid completed current lesson supplies it again. Historical answer events and completion versions remain intact. This can make an updated concept due again, which is the visible consequence of correcting material. Shared concepts yield one active due item per course.

The local identity ledger records accepted pack, lesson-version, question-version, recording, and segment fingerprints by course. A previously accepted identity cannot silently change after switching to another course and back. An exact previously accepted pack can be reactivated; an unrecognized older version or a changed immutable identity is rejected before activation. The importer supports one active course at a time, while course-scoped learner history persists locally. Audio selection, full-mode preference, and resume offsets use course-qualified recording/segment keys; the known fixture's older preferences are read only for `controls-course`. The preference-key hash identifies saved UI state, not audio bytes.
